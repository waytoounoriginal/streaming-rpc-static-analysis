\section{Case Study, Empirical Evaluation, and Discussion}
\label{ch:case-study}

This section evaluates our schema compiler and Clang AST bug finder across our internal test gates and the $26$-handler evaluation corpus in Table~\ref{tab:eval-suites}, testing \textbf{H1}--\textbf{H4} (Section~\ref{ch:related-work}). All runs followed the hardware, compiler, and timing protocol of Section~\ref{sec:exp-design}.

\subsection{Internal Suites, Schema Compilation, and Controlled Evaluation}
\label{sec:controlled-eval}

Before running Dataset~1 and Dataset~2, all three internal sanity gates passed cleanly without hitting the loop-state limit: $9/9$ tests in the schema compiler unit suite ($15.54$\,s), $21/21$ in the AST property suite ($0.94$\,s), and $14/14$ in the Reconstructed Regression smoke gate (peaking at $3$ loop states on unit tests and $4$ on regression vs.\ the $64$-state cap). Compiling Protobuf \texttt{MethodOptions} into client and dual server DFSM sidecars took roughly a millisecond or less (median over $3$ warm-up and $15$ timed runs): $0.354$\,ms ($\mathrm{IQR}=0.016$\,ms) for \texttt{HandshakeService} ($1$ option line, $6$ states and $6$ transitions per role), $0.380$\,ms ($\mathrm{IQR}=0.013$\,ms) for \texttt{ConfigStreamer} ($1$ option line, $5$/$5$), $0.573$\,ms ($\mathrm{IQR}=0.022$\,ms) for WeNet \texttt{ASR.\allowbreak Recognize} ($1$ option line, $5$/$6$ client and $4$/$5$ server), and $1.192$\,ms ($\mathrm{IQR}=0.378$\,ms) for the six-RPC OSS schema bundle ($7$ option lines, $28$ client states and $31$ transitions). This meets \textbf{H1} for C++ call-site intrusiveness: handlers needed $0$ C++ edits and $0/100$~LOC inline annotations ($\rho_{\mathrm{C++}}=0$), shifting specification effort into $1$--$2$ Protobuf option lines per custom RPC ($0$ for default Level~1).

\paragraph{False-Positive Root Causes on Controls (\textbf{H4}).}
Without repo-specific heuristics, Specificity on confirmed safe controls was only $2/7 = 0.286$ ($95\%$ CI $[0.037, 0.710]$), falsifying \textbf{H4}. Only \texttt{OSS-02} (\texttt{GrpcResultStream}), whose RAII destructor pairs \texttt{TryCancel()} with \texttt{Finish()}, and \texttt{OSS-14} (\texttt{buildbox upload}), whose self-contained lambda runs \texttt{Write()}, \texttt{WritesDone()}, and \texttt{Finish()} in one scope, passed cleanly. The other $5$ controls produced $11$ false-positive error diagnostics for three structural reasons:
\begin{enumerate}
    \item \emph{Cross-thread stream lifecycles ($3$ errors across \texttt{OSS-06}, \texttt{OSS-08}):} WeNet \texttt{GrpcClient} (\texttt{OSS-06}, $2$ errors) spawns a background \texttt{std::thread} running \texttt{ReadLoopFunc} and joins it before \texttt{Finish()}. Checking \texttt{Connect}, \texttt{SendBinaryData}, and \texttt{Join} one method at a time misses the concurrent read loop. Triton (\texttt{OSS-08}, $1$ error) similarly splits \texttt{StartStream}, \texttt{StopStream}, and \texttt{AsyncStreamTransfer} across a \texttt{joinable()} worker thread.
    \item \emph{Helper wrappers and split caller/callee protocols ($6$ errors across \texttt{OSS-10}, \texttt{OSS-11}):} In \texttt{google-\allowbreak cloud-\allowbreak cpp}, \texttt{InsertObjectMedia} (\texttt{OSS-10}, $3$ errors) delegates stream creation and watchdog callbacks to helper functions before looping, while \texttt{UploadChunk} (\texttt{OSS-11}, $3$ errors) runs mid-session on the caller's stream without knowing whether the caller already satisfied the first-\texttt{Write} \texttt{write\_\allowbreak object\_\allowbreak spec} rule.
    \item \emph{Member boolean guards ($2$ errors plus $1$ warning on \texttt{OSS-13}):} Arrow Flight's \texttt{DoFinish()} (\texttt{OSS-13}) tracks completion through a class field \texttt{bool finished\_} and is checked from \texttt{S0\_\allowbreak READING} under the default Level~1 \texttt{SERVER\_\allowbreak STREAMING} model, producing $2$ false-positive unfinalized/non-\texttt{eos} errors plus a \texttt{CONDITIONAL\_\allowbreak VERIFICATION} warning (\texttt{Receive\allowbreak Complete=\allowbreak Unknown}).
\end{enumerate}

\paragraph{Qualitative Review of Unconfirmed Category~D Anomalies.}
The checker flagged all $9$ Category~D targets ($30$ error diagnostics) whose local symptoms were reproduced in standalone \texttt{libgrpc++ 1.72.0} loopback harnesses. Because upstream maintainers have not reviewed these findings, they remain unconfirmed anomalies rather than accepted bugs---especially where omitting \texttt{Finish()} on an error path relies on \texttt{\~{}ClientContext()} cancellation as an intentional cleanup tradeoff:
\begin{itemize}
    \item \emph{Omitted \texttt{Finish()} on early exits or middleware (\texttt{OSS-01}, \texttt{OSS-03}, \texttt{OSS-04}, \texttt{OSS-12}):} \texttt{Caching\allowbreak Interceptor::\allowbreak Intercept} (\texttt{CD-01}, \texttt{OSS-01}) writes and reads on a cache miss without calling \texttt{Finish()}, producing HTTP/2 \texttt{RST\_STREAM(8)}, skipping \texttt{POST\_RECV\_\allowbreak STATUS}, caching empty reads, and overwriting the final status with \texttt{OK}. Arrow's \texttt{ListFlights} (\texttt{CD-02/03}, \texttt{OSS-03}), \texttt{Authenticate\allowbreak Internal} (\texttt{CD-05/06}, \texttt{OSS-04}), and \texttt{ListActions} line~939 (\texttt{CD-04}, \texttt{OSS-12}) exit early via \texttt{RETURN\_\allowbreak NOT\_\allowbreak OK} before \texttt{Finish()}, bypassing \texttt{CallCompleted} middleware hooks. On \texttt{OSS-12}, the checker also flagged \texttt{FromProto(ActionType)} at line~935 (\texttt{FP-01}); although reachable in the AST, that overload unconditionally returns \texttt{Status::OK()}, making the path infeasible at runtime.
    \item \emph{Multi-step teardown and exception-unwinding leaks (\texttt{OSS-05}, \texttt{OSS-15}, \texttt{OSS-16}):} The destructor \texttt{\~{}Grpc\allowbreak Staged\allowbreak Directory} in BuildBox (\texttt{CD-07}, \texttt{OSS-05}) sends an empty cleanup message and calls \texttt{WritesDone()} without reading the acknowledgment or calling \texttt{Finish()}, causing \texttt{RST\_STREAM(8)} and restage races. Two other methods, \texttt{uploadFdRegion} (\texttt{CD-08}, \texttt{OSS-15}) and \texttt{download} (\texttt{CD-09}, \texttt{OSS-16}), skip \texttt{Finish()} when uncaught \texttt{std::\allowbreak system\_error} exceptions unwind the stack; \texttt{OSS-16} also emits \texttt{CONDITIONAL\_\allowbreak VERIFICATION} (\texttt{Receive\allowbreak Complete=No}) at line~395 because its normal path calls \texttt{Finish()} without draining \texttt{Read} to \texttt{eos}.
    \item \emph{State corruption and empty-stream abort (\texttt{OSS-07}, \texttt{OSS-09}):} Distinct from missing-\texttt{Finish()} teardown paths, WeNet's gRPC server handler (\texttt{CD-12}, \texttt{OSS-07}) hits \texttt{CHECK(\allowbreak feature\_\allowbreak pipeline\_ != nullptr)} and aborts if a client half-closes an empty stream before sending a config frame (\texttt{exit\_\allowbreak code=3}). In Triton (\texttt{CD-11}, \texttt{OSS-09}), calling \texttt{AsyncStream\allowbreak Infer} after \texttt{StopStream()} invokes \texttt{Write()} on a closed handle; \texttt{libgrpc++} returns \texttt{false} cleanly but leaves an unpopped \texttt{Request\allowbreak Timers} entry in client telemetry.
\end{itemize}

\subsection{Findings Summary and Threats to Validity}
\label{sec:discussion-conclusion}

Our results evaluate \textbf{H1}--\textbf{H4} as follows:
\begin{itemize}
    \item \textbf{H1 (Met for C++ Source Edits):} External Protobuf \texttt{MethodOptions} and \texttt{grpc.session.v1} sidecars required $0$ C++ source edits ($\rho_{\mathrm{C++}}=0/100$~LOC across $352$ Dataset~1 SLOC and $985$ Dataset~2 SLOC), shifting specification work to $1$--$2$ option lines per custom RPC in \texttt{.proto} ($0.35$--$1.19$\,ms compile time).
    \item \textbf{H2 (Passed on Controlled Suite):} On the $N=10$ author-written Dataset~1 suite, every planted case passed ($\mathrm{TP}_h=6/6$, 95\% CI $[0.541, 1.000]$; $\mathrm{TN}_h=4/4$, 95\% CI $[0.398, 1.000]$) with $\mathrm{FP}_v=0$ errors on controls, though self-validation limits generalization to real-world Recall.
    \item \textbf{H3 (Falsified):} Paired end-to-end build overhead over plain \texttt{clang++ -fsyntax-only} was $O_{\mathrm{build}}=3.95\%$ ($\mathrm{IQR}=0.92\%$, range $2.22\%$--$6.75\%$), exceeding the $<1\%$ threshold. Because the AST traversal itself took only $2.95$\,ms pooled median, \texttt{-Xclang -ast-dump=json} serialization dominates total overhead ($\sim 150$--$200$\,ms); an in-process Clang \texttt{ASTConsumer} would avoid JSON serialization.
    \item \textbf{H4 (Falsified):} Unmodified single-function checking reached only $\mathrm{Specificity}=2/7=0.286$ ($95\%$ CI $[0.037, 0.710]$), well below the $\ge 0.80$ threshold. The $5$ false-positive controls show that intraprocedural analysis alone is too noisy for unassisted CI gating on code using background threads, wrapper helpers, and member boolean flags.
\end{itemize}

\paragraph{Threats to Validity.}
(1)~\emph{Missing baselines:} We did not benchmark against Clang Static Analyzer's \texttt{StreamChecker}, \texttt{clang-tidy}, CodeQL, Infer/Pulse, or a trivial ``every stream calls \texttt{Finish()}'' leak rule, so the incremental value of session-type DFSMs over simpler leak checkers remains unmeasured. (2)~\emph{Construct and provenance limits:} Dataset~1 ($N=10$) is self-authored (wide 95\% CIs) and Dataset~2 contains $N_{\mathrm{conf}}=0$ upstream-confirmed bugs; Category~D omissions like skipped \texttt{Finish()} on error paths may be considered acceptable \texttt{\~{}ClientContext()} cleanup rather than defects by maintainers, and external \texttt{.proto} spec authoring error rates were not studied. (3)~\emph{Timing scope:} Dataset~1's $O_{\mathrm{build}}=3.95\%$ reflects filtered AST JSON dumping (\texttt{-ast-dump-filter=Run}); unfiltered full-TU JSON dumps on real code (up to $20.9$\,MB and $61.7$\,ms decode on Triton) would add larger serialization cost, and Dataset~2 timings measure cached JSON decoding ($R_2=22.3\%$--$24.3\%$) rather than full upstream builds. (4)~\emph{External and soundness limits:} The tool is a finite-state intraprocedural bug finder with no soundness theorem or formal equivalence proof against \texttt{libgrpc++}, no distributed deadlock proof, a $64$-state loop limit, loopback rather than distributed test servers, and no thread, alias, or async \texttt{CompletionQueue}/callback reactor support.
